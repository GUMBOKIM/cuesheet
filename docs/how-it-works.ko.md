## 상태는 하나, 바꾸는 길은 셋

cuesheet가 하는 일은 전부 `CueState` 객체 하나가 정합니다. 핸들러마다 어떤 시나리오로 응답할지, 지연,
시계, 오프라인 여부가 다 여기 들어 있습니다.

패널, `?cue=` 링크, 코드 API(`window.__cuesheet__`, `select()`, `patch()`)는 모두 이 객체 하나를 읽고
씁니다. 그래서 패널에서 고른 시나리오가 공유 링크에 그대로 들어가고, 테스트도 사람과 같은 화면을 봅니다.

상태는 메모리에 있습니다.

- 영구 저장소를 쓰면(예: `storage: window.localStorage`) 바뀔 때마다 거기에도 써 두니까 새로
  고침해도 상태가 남습니다.
- 저장에 실패해도 새로 고침 전까지는 전부 그대로 동작합니다.
- 탭마다 상태를 따로 가지고, 탭이 로드될 때 저장소에 있던 값이 이깁니다.

## 요청 파이프라인

cuesheet가 꺼져 있으면 모든 요청이 곧바로 네트워크로 나갑니다(플러그인의 `onRequest`는 그래도 실행됩니다).
켜져 있으면 이렇게 흘러갑니다.

```text
요청 ─▶ plugin.onRequest ─▶ 오프라인? ─── 예 ─▶ 지연 ─▶ TypeError로 실패 ─▶ 기록 · plugin.onError
                                 │
                               아니오
                                 ▼
                  켜진 핸들러 중 매칭되는 게 있나?
                                 │
               ┌────── 예 ───────┴────── 아니오 ──────┐
               ▼                                      ▼
              지연                        실제 네트워크(기록 안 함)
               │
               ▼
              응답 ─▶ 기록 · plugin.onResponse
```

- **플러그인은 자기 컨텍스트를 넘겨받습니다.** `onRequest`의 반환값은 `onResponse`나 `onError`로
  넘어가니, 플러그인이 둘을 이으려고 따로 저장소를 둘 필요가 없습니다.
- **응답을 붙잡지 않습니다.** 앱은 `onResponse` / `onError`가 실행되기 전에 응답(이나 실패)을 받습니다.
  그래서 기록이나 로그를 위해 본문을 읽어도, 스트리밍 응답이라도 응답을 붙잡지 않습니다.
- **본문은 cuesheet가 응답한 요청에서만 읽습니다.** 최대 1 MiB, 길어야 1초 동안 읽습니다.
- **`onRequest`는 가로챈 모든 요청에서 실행됩니다.** 결국 실제 네트워크로 나갈 요청과 cuesheet가 꺼져
  있을 때의 요청까지 포함하니 가볍게 유지하세요.
- **지연 중에 abort하면 바로 기다림을 멈춥니다**(fetch든 XHR이든, 그래서 axios 취소도). 요청은 실패하고
  기록에 남지 않습니다. 인터셉터가 `xhr.abort()`를 전달하지 않아서, cuesheet가 가로챈 XHR마다
  `abort()`를 감싸 알아챕니다.
- **플러그인이 예외를 던져도 괜찮습니다.** 요청과 나머지 플러그인은 그대로 진행됩니다.
- **상태는 요청마다 새로 읽습니다.** 바꾸면 바로 다음 요청부터 적용됩니다.

> [!WARNING]
> 스트리밍에서 XHR은 예외입니다. 인터셉터가 목 본문의 길이를 먼저 잰 뒤 XHR에 넘기기 때문에, XHR은
> 스트리밍 응답을 끝난 뒤에야 받습니다. fetch는 오는 대로 받습니다.

## 서비스 워커를 쓰지 않는 이유

브라우저에서 MSW는 보통 서비스 워커로 동작합니다. cuesheet는 그렇게 하지 않습니다.

- Capacitor 앱의 릴리스 WebView가 서비스 워커의 fetch 가로채기를 막습니다
  ([ionic-team/capacitor#7069](https://github.com/ionic-team/capacitor/issues/7069)).
- 그렇다고 웹에서만 서비스 워커를 쓰면 전송 경로가 둘로 갈립니다.

그래서 [`@mswjs/interceptors`](https://github.com/mswjs/interceptors)로 `fetch`와 `XMLHttpRequest`를
직접 패치합니다. 이 방식은 양쪽에서 다 됩니다. 핸들러는 그대로 평범한 MSW 핸들러입니다.

## 한계

- **페이지 안의 `fetch`와 `XMLHttpRequest`만 가로챕니다.** axios는 브라우저에서 XHR을 쓰니까 여기
  들어갑니다. `<img>`, CSS, `<script>`가 보내는 요청은 안 들어가니, 이런 요청에는 DevTools의 네트워크
  스로틀링을 쓰세요.
- **브라우저 전용입니다.** 서버에서 보내는 요청(Next.js Server Components, Route Handlers)은 가로채지
  않습니다. `start()`는 브라우저 밖에서 경고만 남기고 아무것도 하지 않으니, SSR 중에 인스턴스가
  import돼도 서버의 `fetch`나 `Date`를 건드리지 않습니다. 상대 경로 핸들러 URL을 매칭하려면 페이지
  origin도 있어야 해서, 순수 Node 환경의 요청에는 응답하지 않습니다.
- **시계는 앱이 이미 읽은 날짜를 못 바꿉니다.** 앱이 부팅되기 전에 적용되도록 `?cue=time:...`으로
  진입하세요. 그보다 먼저 원래 `Date`를 잡아 둔 코드(`const now = Date.now`, `class X extends Date`)와
  인자 없는 `Intl.DateTimeFormat#format()` 같은 엔진 내부 동작은 실제 시간을 그대로 씁니다.
- **고정된 시계에서는 `Date.now()`로 경과 시간을 재는 코드가 멈춥니다.** `setTimeout`은 그대로 울리지만
  흐른 시간이 늘 0이라, lodash `debounce` / `throttle`은 끝내 호출되지 않습니다. 디바운스된 검색창이나
  자동 저장이 아무 일도 하지 않는다는 뜻입니다. 그런 화면에는 `time:.../running`을 쓰고, 고정 시계는
  정확한 경계를 볼 때만 쓰세요.
- **흐르는 시계는 적용될 때마다 `time:` 값에서 다시 시작합니다.** cuesheet를 껐다 켜거나, `stop()` 후
  `start()`하거나, `time`을 다시 설정하면 `Date.now()`가 그 시각으로 돌아갑니다. 그래서 같은 링크는 늘
  같은 시각에서 열립니다. 이 사이에 걸쳐 타임스탬프를 비교하는 코드는 시간이 거꾸로 간 것처럼 봅니다.
- **cuesheet가 응답한 요청은 DevTools Network 패널에 안 보입니다.** 네트워크에 나가지 않기 때문입니다.
  요청 기록이나 패널의 요청 목록을 보세요.
- **지연은 cuesheet가 응답하거나 끊은 요청에 적용됩니다.** 실제 네트워크로 나가는 요청에는 적용하지
  않습니다. 거기엔 이미 실제 지연이 있으니까요.
- **지연은 타임아웃이 아닙니다.** cuesheet가 응답하는 요청에서는 `xhr.timeout`(axios의 `timeout` 옵션이
  설정하는 값)이 발생하지 않습니다. 아래에 깔린 `@mswjs/interceptors`가 이를 흉내 내지 않고, msw도
  마찬가지입니다. 그래서 `axios.get(url, { timeout: 1000 })`에 `delay:5000`을 걸어도 5초 뒤 응답이
  그대로 도착합니다. 타임아웃 처리를 확인하려면 `HttpResponse.error()`를 반환하는 시나리오를 쓰거나
  `offline`을 켜세요.
