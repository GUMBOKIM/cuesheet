# For agents working on this app

This is a coupon app. Change requests live in `requirements/CR-*.md`, and each request's acceptance
criteria are written as tests in `e2e/cr/cr-*.spec.ts`. **When you take a CR, you are done when its
spec passes.**

## Workflow

1. Read `requirements/CR-N.md`. The `?cue=` values in its acceptance table define "in which state"
   exactly.
2. Implement it. App code is in `src/`; mock responses are in `src/mocks/handlers/*.mock.ts` (one file
   per API). If the requirement talks about a new response (e.g. a 409), **add a scenario to that API's
   handler file**. For a new API, create a new file — registration is automatic.
   `src/cuesheet-env.d.ts` is regenerated by the dev server from the handlers. **The tests start a dev
   server too, so running the tests updates this file.** Don't edit it by hand; if it changed, include
   the change.
3. Check it in the browser (see "Checking with cuesheet" below).
4. `pnpm test:cr cr-N` must pass, and `pnpm test:e2e` (existing behaviour) must keep passing.
   Running `pnpm test:cr` with no argument also shows failures from other, unimplemented CRs — that is
   expected.

Don't change the specs in `e2e/`. If you think a spec is wrong, don't fix it — report why.

## Running

From the repository root:

```bash
pnpm install
pnpm build                                   # build the cuesheet packages (the example uses dist, like a published package)
pnpm --filter cuesheet-example-react dev     # to look by hand: http://localhost:5173
```

In this folder:

```bash
pnpm test:e2e        # existing behaviour (must always pass)
pnpm test:cr cr-1    # CR-1 acceptance criteria
```

The tests start their own dev server (port 5174 by default) and reuse one if it is already running
there. **If several workers run on the same machine at once, give each a port, e.g.
`PORT=5201 pnpm test:cr cr-1`.** Otherwise tests attach to someone else's worktree.

## Checking with cuesheet

cuesheet decides this app's API responses, clock and network. **Read `node_modules/cuesheet/AGENTS.md`
before starting** — it covers entering a state with `?cue=`, `select` / `patch`, reading request
records, and the behaviour to expect. `window.__cuesheet__.help()` prints a short version with this
app's handlers.

For this app:

```ts
// /?cue=on,time:2026-01-29T09:00:00Z
// /?cue=on,redeemCoupon:Server error
// /?cue=on,offline
window.__cuesheet__.select('getCoupons', 'Empty')
window.__cuesheet__.getRecords({ handlerId: 'redeemCoupon' })
```

- **The list follows state changes by reloading.** The app calls `cuesheet.subscribe(load)`, reloads the
  list (aborting a load still in flight) and reads `Date.now()` again while rendering. Components don't notice the clock changing on
  their own.
- The test helpers in `e2e/cue.ts` (`enter`, `select`, `patch`, `records`, `lastRequest`,
  `scenariosOf`) wrap `window.__cuesheet__`. Use them in specs.

## Watch out

- **Keep cuesheet behind `import.meta.env.DEV`.** `src/main.tsx` loads `src/mocks/cuesheet.ts` with a
  dynamic import on the dev server only and passes the instance to `App` (`undefined` in production builds).
  A static import of `cuesheet`, a handler file or `@cuesheet/react` from app code puts mocks in the
  production bundle.
- **Without a pinned clock every coupon looks expired.** Fixture expiry dates are fixed in Jan–Mar
  2026. The test helper `enter()` pins the clock to `2026-01-15` when there is no `time:`.
- Mock responses never hit the network, so they don't show in the DevTools Network tab. Use
  `getRecords()`.
- Requests cut by offline fail before a handler is chosen, so their records have no `handlerId`. Find
  them with `{ method, path, failed: true }`.
